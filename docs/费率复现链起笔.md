# 费率复现链起笔 · queued 强平单点执行

> 案名：强平执行案（标签 `强平执行案` / basispad-03）
> 本文只复现强平这一条链，不涉及结算封批、不涉及锁期禁撮。那两处的句子不要粘进本文。

## 0. 现场

- `data/app.db` 中 `LIQ-0001`（簿 2、标的 3、数量 50、触发标记 120）状态 `queued`；
- 保证金页该簿已被标成 `liquidated`（假绿）；
- 成交回报里没有 `source='liquidation'` 的行；
- 仓位边仍挂旧名义 50。

起点动作：在保证金强平页对 `LIQ-0001` 点「执行强平」。

## 1. 失败测甲：无成交却改状态

复现：把 `fills` 写口打坏（测试中用触发器模拟），再点执行。

修复前的错误表现：
- 异常被 `finally` 里的无条件 `commit()` 吞掉；
- 队列被改成 `executed`，保证金被写成 `liquidated`；
- 成交行不存在，仓位边没动 → 「无成交却改状态」。

期望：执行失败即整笔零增，队列仍 `queued`，成交零增，仓位零改，保证金零改。
红测：`tests/feat_liq_fill_write.py`。

## 2. 失败测乙：把影子强平当已清算

复现：队列仍 `queued`（或被打成 `shadow_draft`），直接把 `margin_states.status`
写成 `liquidated`，页面就显示已清算。

期望：
- 保证金页只认正式凭据（成交 + 仓位边 + 队列 `executed`）；
- 无凭据的 `liquidated` 一律降级显示，并在 `/api/audit/liq_recon` 报
  `liquidated_without_fill` / `executed_without_fill` / `unexpected_liq_status`；
- 影子草案不得冒用正式状态。

红测：`tests/feat_liq_margin_fake.py`。

## 3. 争用失败测：双会话抢「强平执行互斥」

复现：`trader` 与 `admin` 两个会话同时对同一 `LIQ` 单点执行。

修复前的错误表现：
- 旧 `acquire_lock` 在业务事务内抢锁，锁行在提交前对另一连接不可见；
- 两个会话都读到 `queued`，都往下写 → 双成（两笔强平成交、仓位扣两次）。

期望：
- 抢锁在独立事务内提交，抢到即对其他会话可见；
- 一成一败（`200` / `409`）；
- 败方零正式改，只留 `execute_contended` 争用痕（取舍另在交班说明写，不入正式表）；
- 锁不残留。
- 并发入口封装为 `race_liq_execute`（`tests/feat_liq_race.py`）。

## 4. 验收口径（合入门槛）

1. 执行后必有 `liquidation` 成交（`fills.source='liquidation'`，`note` 回指 `LIQ` 编码）；
2. 仓位与保证金同源：`positions.qty` 与 `margin_states.used_margin` 同事务更新，
   页面读取时仍按仓位边实时推导；
3. 落败会话只留痕：正式表零改，`audit_logs` 有 `execute_contended`；
4. 写口绿（`margin_svc`）与对账绿（`audit_svc`）分属异服务；
5. 三份红测齐套且全绿后，才允许改策略簿服务、审计服务、锁服务、保证金服务、
   撮合服务与成交回报页、保证金强平页。

## 5. 收工自检

逐页打开：策略纸面簿页、委托撮合页、总览页、保证金强平页、成交回报页。
并发用 `race_liq_execute` 压锁。禁止跳过红测链。

## 6. 交班单

- 成交号：执行返回的 `fill_code`；
- 仓位边差额：执行返回的 `position_delta`；
- 剩余仓位：`remaining_qty`；
- 保证金占用：执行后 `margin_states.used_margin`（应为 0 或按剩余仓位）；
- 争用：若本次是败方，只写争用痕；正式区零改。
